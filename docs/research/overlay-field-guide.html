Building an interactive overlay with an automatic checklist

How overlay apps sit on top of the game, which game events an outside program can legitimately see, and how to turn those events into a checklist that ticks itself. Event formats below were checked against the real Client.txt on this Mac.

Short answer

YesAn interactive overlay is very doableIt is a normal transparent, always-on-top desktop window. It never touches the game process. Awakened PoE Trade and Exile-UI already work this way.
Yes, with limitsYou can track events for an auto-checklistThe game writes a live log file. Zone changes, level-ups, deaths, quest skill points, passive allocations and NPC dialogue all appear in it.
Not availableNo kills, loot or quest-state feedThere is no event for monster kills, item pickups or a quest log. You infer progress from zones, rewards and dialogue, and keep a manual tick as fallback.

What GGG allows

Grinding Gear Games publishes a third-party policy in its developer docs. It does not approve individual tools, and staff on the forum decline to confirm whether any given tool is safe. The policy text is still clear about where the lines are.

StatusWhatWhy
PermittedA separate program that draws its own window over the gamePolicy: executable apps that run independently from the game are "permitted" though not encouraged.
PermittedReading the game's log filePolicy says reading log files is okay "as long as the user is aware of what you are doing with that data."
PermittedReading the clipboard after the player presses Ctrl+C on an itemBuilt-in game feature. This is how every price checker works.
RestrictedSending keystrokes or chat commands to the gameOnly when the player triggers it by hand, and one game action per press. Timers, file-change triggers and screen-reading triggers are not allowed to fire inputs.
Grey areaLooking at screen pixels or OCR to update your own UINot named in the policy. Exile-UI does it only to detect open panels and says it avoids reading game values or bars. Never use it to trigger input.
ForbiddenReading game memory, injecting code, hooking the renderer, editing game files, packet sniffingApps that interact with the game or its files break Terms of Use 7b, 7c and 7i. Policy: this "will result in immediate account termination."

What this means for an auto-checklist. A checklist that reads the log and updates its own window sends nothing to the game, so the macro rules never come into play. That is my reading of the policy, not a ruling from GGG. The one thing to avoid is letting a log event fire a keystroke or chat command automatically: the policy names file-change reactions as a banned trigger.

How an overlay works

There is no special game API involved. The overlay is a second window owned by your app, placed exactly over the game window, with a transparent background and a flag that keeps it above other windows.

The four things every overlay has to get right

  1. Display mode. The game must run in Windowed Fullscreen or Windowed. Exclusive Fullscreen can cover every desktop window, including always-on-top ones. Awakened PoE Trade states the same requirement.
  2. Click-through. The window ignores the mouse by default and re-enables it when the pointer is over an interactive element. In Electron this is setIgnoreMouseEvents(true, { forward: true }), where forward keeps hover events flowing so you can detect the pointer entering the panel.
  3. Focus. Clicking the panel must not pull keyboard focus away from the game, or your character stops responding until you click back. Use a non-activating window (focusable: false, or a panel-type window on macOS). Only take focus when the player needs to type into the overlay, then hand it back.
  4. Following the game. Show the overlay only while the game is the foreground window, and match its position and size. Hide it when the player alt-tabs. The electron-overlay-window library does this by finding the game window by title.

Game events you can read

Four sources are available to an outside program. Only the first gives you a live event stream.

Area ids are the key to campaign tracking

The id inside Generating level … area "…" is unique per zone, unlike the display name. Campaign ids follow part_act_zone: part 1 is acts 1 to 5, part 2 is acts 6 to 10. I paired each id with the name that followed it in your log and found 152 distinct campaign ids. Act 1 as an example:

Source 2: clipboard

Pressing Ctrl+C over an item copies its full text description to the clipboard, and Ctrl+Alt+C copies an extended version. Your app can watch the clipboard and parse that text. Useful for "pick up a 4-link" or "find boots with movement speed" checklist items that the player confirms by hovering and pressing a key.

Source 3: official web API

GGG's OAuth API returns account data on request: characters with their equipment and passives (account:characters), stash tabs (account:stashes), atlas passives (account:league_accounts). A desktop app counts as a public client: Authorization Code with PKCE, a local redirect such as http://127.0.0.1:8080/callback, 10-hour access tokens, and rate limits shared across all public clients.

Registration is closed right now. The developer docs currently say GGG is "unable to process new applications." Plan the first version without the API. It is a snapshot source anyway, with no quest state and no push events, so the checklist does not depend on it.

Source 4: looking at the screen

Screen capture with pixel checks or OCR can tell you that the inventory is open or which tooltip is showing. It is fragile across resolutions and UI scale, costs CPU, sits in the grey area of the policy, and on macOS needs the Screen Recording permission. Leave it out until the log proves insufficient for a specific feature.

What you cannot detect

  • Monster and boss kills. Nothing is logged. Use the next zone, a reward line, or boss dialogue as a stand-in.
  • Item pickups and drops. Not logged. Clipboard on demand is the only route.
  • Quest state. No quest log is exposed. Skill point lines and /passives cover the quests that grant points. Others need zone inference or a manual tick.
  • Waypoints, gems socketed, flasks used, current life. Not logged, and reading them from memory is the forbidden path.
  • Which character is logged in. The log does not announce it at login. You learn the name from the first level-up or death line, or you ask the player to pick.

Auto-checklist design

Model each step as text plus a completion condition. The engine holds a pointer to the current step and compares every incoming event with the conditions of the next few open steps.

// one act of a campaign checklist
[
  { "id": "a1-town",   "text": "Reach Lioneye's Watch",   "when": { "type": "area",  "id": "1_1_town" } },
  { "id": "a1-coast",  "text": "Enter The Coast",         "when": { "type": "area",  "id": "1_1_2" } },
  { "id": "a1-lvl2",   "text": "Reach level 2",           "when": { "type": "level", "min": 2 } },
  { "id": "a1-island", "text": "Enter The Tidal Island",  "when": { "type": "area",  "id": "1_1_2a" } },
  { "id": "a1-hail",   "text": "Kill Hailrake",           "when": { "type": "manual" } },
  { "id": "a1-point",  "text": "Hand in to Bestel for the skill point",
                       "when": { "type": "points", "kind": "Passive Skill" } },
  { "id": "a1-mud",    "text": "Enter The Mud Flats",     "when": { "type": "area",  "id": "1_1_3" } }
]

Rules that make it feel reliable

  • Look ahead, not just at the next step. Players skip and reorder. If an event matches a step a few places ahead, complete it and mark anything skipped as "inferred" in a different colour.
  • Every step can be ticked and unticked by hand. Click on the panel or a global hotkey. Automatic detection is an assist, never the only way forward.
  • Key on area id, not name. Take the id from the Generating level line and treat the following You have entered line as confirmation.
  • Ignore noise zones. Hideouts, towns you revisit and map ids should not move a campaign pointer.
  • Offer a resync. When the player types /passives, read the quest names that follow and tick every matching quest step at once. If you bind that command to a hotkey, the player must press it: one press, one chat command, which is what the macro rule permits.
  • Catch up on start. On launch, scan backwards through the tail of the log to the last LOG FILE … OPENING line and replay those events, so opening the overlay mid-session still shows the right state.
  • Save per character. Store progress keyed by character name, learned from level-up or death lines, with a manual picker as fallback.
  • Tell the user what you read. The policy's one condition for log reading is that the user is aware of it. A first-run notice covers that.

Starter code

Three small pieces in TypeScript for Electron. The parser patterns are the ones tested against your log.

1. Overlay window

// main.ts
import { app, BrowserWindow, ipcMain, screen } from 'electron'

app.whenReady().then(() => {
  const { bounds } = screen.getPrimaryDisplay()
  const win = new BrowserWindow({
    ...bounds,
    transparent: true, frame: false, hasShadow: false,
    resizable: false, skipTaskbar: true,
    focusable: false,                 // clicks never steal focus from the game
    webPreferences: { preload: __dirname + '/preload.js' },
  })
  win.setAlwaysOnTop(true, 'screen-saver')
  win.setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })  // macOS Spaces
  win.setIgnoreMouseEvents(true, { forward: true })                 // click-through by default

  // renderer tells us when the pointer is over the panel
  ipcMain.on('overlay:hover', (_e, over: boolean) =>
    win.setIgnoreMouseEvents(!over, { forward: true }))

  win.loadFile('index.html')
})
// renderer: flip click-through as the pointer enters or leaves the panel
const panel = document.querySelector('#panel')!
panel.addEventListener('mouseenter', () => window.overlay.hover(true))
panel.addEventListener('mouseleave', () => window.overlay.hover(false))

For production, swap the fixed primary-display bounds for electron-overlay-window, which attaches to the game window by title and shows or hides the overlay as the game gains and loses focus.

2. Log tailer

// tail.ts: emit each new line appended to Client.txt
import fs from 'node:fs'

export function tail(path: string, onLine: (line: string) => void) {
  let pos = fs.statSync(path).size        // start at the end: the file is large
  let rest = ''
  setInterval(() => {
    const size = fs.statSync(path).size
    if (size < pos) pos = 0                // file was truncated or replaced
    if (size === pos) return
    const buf = Buffer.alloc(size - pos)
    const fd = fs.openSync(path, 'r')
    fs.readSync(fd, buf, 0, buf.length, pos); fs.closeSync(fd)
    pos = size
    const lines = (rest + buf.toString('utf8')).split(/\r?\n/)
    rest = lines.pop() ?? ''               // keep a partial last line for next time
    lines.forEach(l => l && onLine(l))
  }, 250)
}

Polling the file size every 250 ms is more dependable than file-system watch events, which can be delayed or merged while the game holds the file open. Your log is 18 MB, so never read it from the start on each tick.

3. Parser

// parse.ts: turn one log line into a typed event, or null
const LINE = /^(\d{4}\/\d\d\/\d\d \d\d:\d\d:\d\d) \d+ [0-9a-f]+ \[(INFO|DEBUG|WARN|CRIT) Client \d+\] (.*)$/

const RULES = {
  areaGen:  /^Generating level (\d+) area "([^"]+)" with seed (\d+)/,
  entered:  /^: You have entered (.+)\.$/,
  level:    /^: (.+) \((\w+)\) is now level (\d+)$/,
  slain:    /^: (.+) has been slain\.$/,
  points:   /^: You have received (?:an?|(\d+)) (.+?) Points?\.$/,
  passive:  /^Successfully (allocated|unallocated) passive skill id: (\S+), name: (.+)$/,
  questPt:  /^: \((\d+) from (.+)\)$/,
  kitava:   /^: You have been permanently weakened by Kitava's (cruel|merciless) affliction/,
  trade:    /^: Trade (accepted|cancelled)\.$/,
  whisper:  /^@(From|To) (?:<.+?> )?(.+?): (.*)$/,
  loading:  /^\[LOADING SCREEN\] \((.+)\) Duration = ([\d.]+) seconds/,
}
// NPC dialogue has the form "Speaker: text". Match against known names only,
// because engine lines such as "Tile hash: 123" have the same shape.
const NPCS = new Set(['Izaro', 'Einhar, Beastmaster', 'Jun, Veiled Master', 'The Maven'])

export function parse(line: string) {
  const m = LINE.exec(line)
  if (!m) return line.includes('LOG FILE') ? { type: 'clientStart' } : null
  const [, time, , body] = m
  for (const [type, re] of Object.entries(RULES)) {
    const x = re.exec(body)
    if (x) return { type, time, args: x.slice(1) }
  }
  const i = body.indexOf(': ')
  if (i > 0 && NPCS.has(body.slice(0, i)))
    return { type: 'npc', time, args: [body.slice(0, i), body.slice(i + 2)] }
  return null
}

Language matters. These patterns match the English client. System messages are localised, so other languages need their own message strings. The Generating level … area and Successfully allocated passive lines are engine output and I would expect them to stay in English, but I only had an English log to check.

Build order

  1. Log reader in a terminal

    Tailer plus parser printing events while you play. No UI yet. This proves the core idea in an evening.

  2. Bare overlay window

    A transparent Electron window with one box that stays above the game in Windowed Fullscreen. Sort out click-through and focus on your Mac here, before anything else depends on it.

  3. Checklist engine

    Step JSON, rule matching with look-ahead, manual tick, saved state. Unit-test it by replaying slices of your existing log.

  4. Wire them together

    Events from the main process to the renderer over IPC. Act 1 checklist ticking itself is the first real milestone.

  5. Game-window tracking and hotkeys

    Attach to the game window, hide on alt-tab, add a show/hide hotkey and a "tick current step" hotkey.

  6. Content and extras

    Full campaign data from exile-leveling, the /passives resync, passive-tree checklist, clipboard item checks, a checklist editor.
